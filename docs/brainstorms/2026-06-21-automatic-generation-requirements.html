Automatic Generation for Study Areas

CueCraft should let users choose a knowledge area once, then keep the notes inside it ready for active recall without requiring manual generate actions note by note.

Summary

Recommended direction: build Study Area Autopilot, where the user picks a parent folder as a study area, confirms an initial backfill, and lets CueCraft maintain generated cues for notes under that folder with visible progress, retry, pause, and spend guardrails.

The narrower alternatives are a one-time folder backfill or just-in-time generation when a note is opened for review. Those are useful stepping stones, but the study-area framing makes CueCraft feel meaningfully more automatic and helpful.

Problem Frame

CueCraft already generates cues for the active note, refreshes stale sections, and can auto-generate on save. That still leaves a user with a course folder, research folder, or project knowledge base doing setup note by note before the material feels study-ready.

The user-facing pain is not just the click count. It is the uncertainty: which notes have cues, which are stale, which failed, and whether turning on more automation will unexpectedly spend API calls across a large vault.

Candidate Directions

Option 1

One-Time Folder Backfill

Let the user pick a parent folder and generate cues for every eligible Markdown note underneath it once.

  • Pros: Smallest product change; directly answers the parent-folder request.
  • Cons: Notes drift stale again unless the user keeps managing them.
  • Best when: The goal is a low-risk batch generation feature.
Option 2

Just-in-Time Readiness

Generate missing or stale cues when the user opens, reviews, or enters Cornell view for a note in a chosen folder.

  • Pros: Avoids large background runs and limits spend to notes the user actually touches.
  • Cons: The first review of a note can be delayed by generation.
  • Best when: Cost control matters more than having an entire folder ready in advance.
Option 3 - recommended

Study Area Autopilot

Treat a parent folder as a managed study area with initial backfill, ongoing stale-note maintenance, visible queue state, and user-controlled limits.

  • Pros: Makes CueCraft feel automatic while keeping consent and progress visible.
  • Cons: Requires a stronger management surface than a command-only batch run.
  • Best when: The goal is to make CueCraft a study companion, not just a note action.

Recommendation

Choose Study Area Autopilot as the product direction, but ship it in a path that can start as folder backfill. This keeps the first slice practical while preserving the product shape that makes the feature feel automatic over time.

Key Decisions

Frame the feature as study areas, not batch generation

A folder batch command helps once. A study area gives the user an ongoing promise: notes in this learning context are kept ready for review.

Make automation explicit before it spends

The first backfill and any broad ongoing rule must require opt-in, show the affected note count, and provide a pause path.

Reuse current CueCraft surfaces for the payoff

Generated cues should appear through existing editor, Reading mode, Cornell view, review, and export experiences rather than creating a separate study product in v1.

Defer cross-note intelligence

Cross-note synthesis and spaced review queues are attractive follow-ons, but the first automatic generation feature should prove the managed-area loop first.

Requirements

Study area setup

IDRequirement
R1.A user can create a study area from a parent folder, making descendant Markdown notes eligible for automatic cue generation.
R2.CueCraft shows the number of eligible notes before the first broad generation run starts.
R3.A user can exclude specific notes or subfolders from a study area before or after generation begins.
R4.Existing per-note hidden state is respected unless the user deliberately re-enables that note.

Automatic generation behavior

IDRequirement
R5.An initial backfill generates cues for uncued eligible notes and refreshes notes whose cues are stale.
R6.Ongoing maintenance reacts to edits inside enabled study areas without applying save-time generation to unrelated vault notes.
R7.A run can be paused or cancelled while keeping cues already generated during that run.
R8.Failures are isolated per note or section, and the user can retry failed work without repeating successful work.

Study readiness

IDRequirement
R9.CueCraft distinguishes ready, uncued, stale, failed, skipped, and paused notes inside a study area.
R10.Opening a ready note shows CueCraft's existing study surfaces without requiring the user to run Generate first.
R11.After a run, the user can see what changed, what failed, and what remains to do in the study area.

Guardrails

IDRequirement
R12.Automatic generation never modifies source Markdown.
R13.Broad automatic runs require a configured provider and should inherit existing provider setup and parallel-request controls.
R14.The user has a clear global off switch for study-area automation.
R15.The product copy makes API cost and rate-limit risk visible before large automatic runs.

Key Flows

F1. Create Study Area

Trigger: The user chooses to make a parent folder study-ready. CueCraft previews eligible notes, exclusions, and the automation mode before any generation begins.

F2. Initial Backfill

Trigger: The user confirms the run. CueCraft generates uncued notes, refreshes stale notes, isolates failures, and keeps completed notes ready even if the run stops.

F3. Ongoing Maintenance

Trigger: A note inside an enabled study area changes. CueCraft queues the note for refresh according to the user's automation mode and avoids unrelated vault notes.

F4. Review Ready Material

Trigger: The user opens or reviews a ready note. Existing CueCraft study surfaces appear from cache without a manual generate step.

F5. Recover from Failure

Trigger: One or more notes or sections fail generation. CueCraft shows what failed and lets the user retry failed work without repeating successful work.

Acceptance Examples

AE1. Covers R1, R2, R13. Given a user selects a folder with 42 Markdown notes, when the setup preview opens, then no provider calls happen until the user confirms the run.

AE2. Covers R3, R4, R6. Given a note is excluded or hidden, when study-area maintenance runs, then that note is skipped unless the user includes it again.

AE3. Covers R5, R7, R11. Given a backfill is halfway complete, when the user cancels it, then completed note caches remain and the summary shows the remaining work.

AE4. Covers R8, R9. Given one note fails generation while others succeed, when the run finishes, then the study area shows that note as failed and offers retry without redoing successful notes.

AE5. Covers R10, R12. Given a note is ready, when the user opens it, then CueCraft surfaces cached study cues without modifying the Markdown file.

AE6. Covers R14, R15. Given automation is enabled for a study area, when the user turns off automatic generation, then CueCraft stops future background maintenance while preserving existing cues.

Success Criteria

  • A user can make a course or research folder study-ready without opening each note and pressing Generate.
  • A user can tell which notes are ready, stale, uncued, failed, skipped, or paused.
  • A user can stop automation before or during a broad run without losing completed work.
  • The feature preserves CueCraft's non-destructive promise and avoids surprise provider calls.

Scope Boundaries

In Scope

  • Parent-folder based study areas.
  • Initial backfill for uncued and stale notes.
  • Ongoing maintenance for edited notes inside enabled study areas.
  • Pause, cancel, retry, skip, and exclusion behavior.
  • Run summary and readiness state for managed notes.

Deferred

  • Cross-note synthesis across a study area.
  • Spaced-repetition scheduling or external study queue integration.
  • Full-vault automatic generation by default.
  • Complex rules based on tags, backlinks, dates, or query languages.
  • Provider cost optimization beyond visible limits and existing concurrency controls.

Dependencies And Assumptions

  • Users will accept automation when the scope, note count, and cost risk are visible before generation.
  • Parent folders are the right first scoping primitive because they match how students and researchers organize learning material.
  • The current per-note cache, stale detection, and generation settings are good product foundations for a managed-area experience.
  • Planning should verify how the current single active generation run should behave when a study-area run and a note-level run collide.

Outstanding Questions

Resolve Before Planning

  • Should the first shipped slice be Option 1 one-time folder backfill or the recommended Study Area Autopilot foundation?
  • Should ongoing maintenance default to paused after the first backfill, or should the setup ask users to enable it immediately?

Deferred To Planning

  • Where should the study-area management surface live: settings, command modal, status pane, or Cornell view affordance?
  • What is the smallest clear progress model for long-running folder generation?

CueCraft product ideation

Remove the view, keep the study loop

Cornell View now adds navigation without adding enough value as a destination. The removal should preserve its answer-safe recall and cue-repair capabilities inside the note, while deliberately retiring pane-only presentation choices.

Ideation Date: 2026-07-30 Topic: cornell-view-removal Mode: repo-grounded Focus: remove Cornell View and audit unique capabilities

Grounding context

What the code says today

Editing View and Reading mode already render cues, Note Brief, and Section Lens from the same cached cue data and parsed Markdown sections. Cornell View is not a separate data model; it is a custom workspace destination that owns a few interactions and a large amount of presentation.

The decisive gap is Study Mode. reviewThisNote() navigates to Cornell because Cornell is currently the only surface with section-level reveal. Editing Study Mode blurs answers globally but has no reveal action, while Reading mode routes its review affordance back into Cornell.

There is no institutional learning corpus under docs/solutions/. The closest prior internal work is the July 2 settings split, which already separated editor-only, Cornell-only, and cross-surface settings and anticipated this retirement.

Core finding: Cornell View can go, but deleting it first would silently remove active recall and cue maintenance. The safe product move is capability migration followed by destination removal.

1

Capabilities First, View Last

Confidence 94%Complexity High

Entry points, compatibility, and persisted state

Description: Treat removal as a strangler sequence: make answer-safe in-note review and cue repair complete first, then remove Cornell-specific entry points and the functional custom view. The old pane does not survive as a compatibility shell; the replacement behavior must be real before the destination disappears.

Basisdirect: Review currently opens Cornell because it is the only surface where Study Mode is visible, and cue repair actions are also Cornell-only. Removing the view first creates a verified capability gap.
RationaleThis is the highest-leverage direction because it makes every later deletion safe and keeps the product promise intact throughout the transition.
DownsidesThere will be a short period of duplicated behavior and transition code. It requires disciplined scope so “temporary” Cornell paths do not linger.
Meeting testCan Cornell View be disabled after the replacement capabilities ship without removing any study or repair action users can perform today?
2

Review Is a Note State, Not a Place

Confidence 92%Complexity High

Study interaction and answer reveal

Description: Make Review This Note activate a transient study state in the note already on screen. Stable section IDs drive hide, reveal, and reset behavior; Editing and Reading can implement surface-specific adapters without changing Markdown or cue storage.

Basisdirect: Cornell already stores revealed section IDs and computes hidden answer state. Product docs call for one-section reveal and hide-all reset. external: Anki, RemNote, and Cornell Notes Pro place recall in prompt/reveal state rather than destination switching.
RationaleThe learning interaction is the valuable part of Cornell View. Moving that state into the note removes the extra step and restores the intended recall loop.
DownsidesEditing and Reading have different DOM lifecycles, and editor decorations must remain viewport-conscious. Reading source masking is not yet proven locally.
Meeting testCan a user begin a fresh pass, reveal one linked section, reset all answers, and finish review without changing leaves?
3

Cue Repair at the Point of Doubt

Confidence 90%Complexity Medium

Cue maintenance and recovery actions

Description: Make failed and low-confidence cues actionable wherever they are rendered. Retry, tone regeneration, and stale-note recovery belong beside the questionable cue or current-note status, not in a separate workspace toolbar.

Basisdirect: Cornell already implements low-confidence regeneration, tone selection, and retry. Editing and Reading render the same failure/confidence information but currently provide display-only messages.
RationaleThis preserves Cornell's most operational capability while making CueCraft more coherent: the place that identifies a problem also fixes it.
DownsidesControls can clutter compact cue cards. Async regeneration currently refreshes surfaces broadly, so pending and focus behavior need care.
Meeting testCan a user repair a failed or weak cue in place and see the replacement without opening another view?
4

Delete Pane Cosmetics to Clarify the Product

Confidence 88%Complexity Low

Presentation and settings migration

Description: Preserve cue width and font size because Editing View already consumes them. Retire Cornell display mode, accent, border, compact-support, mobile-folding, and paper-style controls unless a native note surface demonstrates a concrete learning use.

Basisdirect: Width and font are applied to editor cue elements. The remaining controls save through Cornell-specific refresh paths or style the dedicated pane.
RationaleRemoval should reduce configuration debt rather than relocate an obsolete view's design system into Editing settings.
DownsidesUsers who customized Cornell's look will lose visible options. Release notes should distinguish removed presentation from preserved study behavior.
Meeting testCan every retained appearance setting be demonstrated on an active Editing or Reading cue?
5

Delete the Adapter, Preserve the Study Kernel

Confidence 91%Complexity Medium

Runtime, test, CSS, and documentation cleanup

Description: Remove the custom ItemView, leaf targeting, dedicated toolbar, Cornell refresh path, pane-only CSS, and destination documentation. Retain and gradually rename shared section identity, cue presentation, support formatting, regeneration, Note Brief, and Hook primitives used by native note surfaces.

Basisdirect: Editing rendering imports Cornell-named support and style helpers, while dedicated view registration and pane CSS have separable ownership boundaries.
RationaleThe name “Cornell” currently mixes a removable transport adapter with shared product primitives. Separating them produces real simplification without collateral regressions.
DownsidesRenaming shared vocabulary can cause unnecessary churn if done all at once. The deletion boundary must be proven by imports and tests, not filenames.
Meeting testDoes the final runtime have no Cornell destination while every shared cue and review primitive still has an explicit owner?
6

Capability Matrix as the Removal Gate

Confidence 87%Complexity Medium

Runtime, test, CSS, and documentation cleanup

Description: Define removal readiness by capability parity across Editing and Reading: reveal/reset, focus navigation if retained, low-confidence repair, failed retry, stale refresh, Note Brief, and Section Lens. Replace destination-shaped tests and docs only after capability-shaped coverage exists.

Basisdirect: Current tests and docs are largely organized around Cornell surface behavior, while shared helpers and CSS serve multiple surfaces.
RationaleA capability matrix prevents both failure modes: deleting shared behavior because it has a Cornell name, and preserving dead code because its tests still pass.
DownsidesIt front-loads verification work before the visible deletion. A matrix can still miss layout and lifecycle regressions without manual Obsidian testing.
Meeting testCan every retained capability point to a native surface test and every deleted module point to a retired product behavior?

Editing Appearance Split

Fresh ideation for splitting the current mixed Appearance settings surface into Cornell Appearance for the Cornell view and Editing Appearance for regular editing-mode cue display.

  • Date: 2026-07-02
  • Topic: editing-appearance-split
  • Focus: Cornell-only vs editing-only appearance settings
  • Mode: repo-grounded

Grounding Context

CueCraft is a TypeScript Obsidian plugin that renders study cues in multiple surfaces: a dedicated Cornell view and normal editing mode through CodeMirror decorations and gutters. The current settings tab has one appearance route and one home card, but that page mixes editor-only controls at the top with Cornell-only thumbnail controls below.

The split is already visible in the code paths. Editor display changes persist editorCueDisplay or editorHookCardStyle and refresh the active editor cues. Cornell appearance changes persist Cornell display, style, width, font, accent, border, or compact-support settings and refresh Cornell views. External prior art from editor platforms supports this surface boundary: editor overlays, custom views, and document presentation are different renderer contracts.

1.

Surface-Named Sibling Pages

Confidence 95% · Complexity Medium

Description: Replace the single Appearance card and route with two sibling destinations: Cornell Appearance and Editing Appearance. The old page becomes Cornell-only, while the new page owns the editor cue display controls currently stranded above Cornell thumbnails. This makes the settings home a surface map instead of a generic theme bucket.

Axis
Settings navigation and naming taxonomy
Basis
direct: the current settings route and home card are singular, the header copy describes Cornell styling, and the page begins with editor-only controls before Cornell controls in src/settings.ts. external: editor platforms such as VS Code separate editor-facing configuration from broader workbench/custom-view configuration.
Rationale
The user problem starts at the first click: "Appearance" sounds global, while the dominant visible page is Cornell-specific and the first two controls are editor-specific.
Downsides
Adding another settings card slightly increases the home grid, so card titles and summaries need to be tight.
2.

Editing Appearance As Editor Cue Studio

Confidence 82% · Complexity Medium

Description: Build the new Editing Appearance page around editor-rendering inputs: cue display mode and rail card background. Keep the page centered on how generated cues appear in the normal editor, not on Cornell layout and not on cue-generation semantics. Treat rail question/support visibility carefully: those are content-visibility decisions and should remain outside this page unless deliberately reframed later.

Axis
Editing cue appearance control surface
Basis
direct: editorCueDisplay and editorHookCardStyle already flow through refreshEditorCues() and the CodeMirror render payload in src/main.ts, src/cue-extension.ts, and src/editor-hook-rail.ts.
Rationale
The strongest page boundary is "only settings that change the editor cue render payload belong here."
Downsides
The first version may feel thin if it only moves two controls, so the preview treatment has to carry the page's value.
3.

Editor Mini-Scenes With Shared Button Chassis

Confidence 88% · Complexity Medium

Description: Reuse the accessible thumbnail-button primitive, but add editor-specific preview recipes that look like CodeMirror editing: a note line, inline cue, gutter/rail state, anchored card rail, and card finish. Cornell previews keep their Cornell scene; editing previews get their own scene model. This keeps the interaction consistent while preventing Cornell miniatures from becoming misleading proxies for editor behavior.

Axis
Preview fidelity, responsiveness, and tests
Basis
direct: src/appearance-thumbnail-controls.ts already provides the shared button primitive, while existing recipes are Cornell-shaped. Editor hook CSS in styles.css already defines a separate visual language for editing-mode rail cards.
Rationale
Editing Appearance only feels real if the preview looks like the editor surface it controls.
Downsides
Requires new preview recipe coverage and CSS. Reusing too much Cornell preview CSS would recreate the confusion.
4.

Cornell Appearance As View-Class Boundary

Confidence 92% · Complexity Small

Description: Rename the existing page to Cornell Appearance and define it as the page for Cornell root classes only: display mode, style, cue width, font size, accent, border, and compact support rendering. Move the low-signal binary controls into a smaller Cornell finishing-details section so they no longer read as global appearance settings. The page should never need the editor cue refresh path.

Axis
Cornell-only appearance containment
Basis
direct: Cornell display/style/layout/accent settings map to Cornell classes in src/cornell-view.ts and Cornell CSS in styles.css, and settings-side Cornell changes call refreshCornellViews().
Rationale
This turns "Cornell-only" from explanatory copy into the page's actual eligibility rule.
Downsides
Some labels may need rewording so "cue column" is clearly Cornell cue column, not editor cue placement.
5.

Surface-Specific Home Summaries

Confidence 90% · Complexity Small

Description: Replace the blended appearanceSummary() with separate summary builders. Cornell Appearance summarizes Cornell display, style, width, font, accent, and finishing details. Editing Appearance summarizes editor cue display and editor card style only.

Axis
Settings navigation and naming taxonomy
Basis
direct: the current summary string joins editor and Cornell values together in src/settings.ts.
Rationale
The settings home should become a boundary validator, not a place where mixed ownership hides in one sentence.
Downsides
Minor copy work, but it needs tests so future summary edits do not drift back to mixed-surface language.
6.

Cue Content Stays Outside Appearance

Confidence 78% · Complexity Small

Description: Keep semantic or content-visibility controls out of both Appearance pages, even when they affect what a preview shows. Controls such as rail question/support visibility, Section Lens visibility, Note Brief visibility, or keyword generation should live in Cue Generation, Note format, or another content-oriented section. Appearance pages remain about renderer presentation, not cue content policy.

Axis
Settings navigation and naming taxonomy
Basis
direct: rail question/support visibility currently maps into the editor render payload, but the verifier found that moving it into Editing Appearance blurs appearance with cue-content semantics. Existing shared review controls already affect multiple surfaces.
Rationale
This protects the user's requested rule: Cornell Appearance affects Cornell view, Editing Appearance affects regular editing display, and content policy lives elsewhere.
Downsides
Editing Appearance may initially have fewer controls. The editor preview can still demonstrate states without adding saved preview-only toggles.
7.

Surface Isolation Test Matrix

Confidence 85% · Complexity Medium

Description: Expand the existing appearance QA into an isolation matrix: editor controls refresh editor cues only, Cornell controls refresh Cornell views only, and neither page renders the other's option recipes. Add responsive, selected-state, keyboard-focus, and dark/light checks for both pages. The split is done when the wrong surface stays unchanged.

Axis
Preview fidelity, responsiveness, and tests
Basis
direct: tests already cover thumbnail selected state and option coverage; editor and Cornell refresh paths are distinct; manual evaluation docs already cover narrow panes and visual states.
Rationale
The likely future regression is leakage: a new setting appears on the wrong page, uses the wrong preview recipe, or refreshes the wrong surface.
Downsides
Some isolation checks may need settings-tab test scaffolding or manual Obsidian review for real CodeMirror layout.

Rejection Summary

#IdeaReason Rejected
1Surface registries / allowlistsWeak. Useful later, but generating whole pages from registries is an implementation abstraction jump beyond the current split.
2Preview-only scenario togglesRefuted. Adds new UI state, overlaps real persisted settings, and over-scopes the narrow appearance split.
3Editing display ladderWeak as a standalone idea. It is folded into Editing Appearance copy and ordering, not promoted as its own direction.
4Viewport-switching editing previewsWeak. Responsive behavior matters, but a visible viewport switcher is more control surface than the evidence justifies.
5Refresh patch bayWeak. The one-refresh-bus rule is valid, but the metaphor is architecture-heavy and better expressed through tests.
6Raw duplicate page-split variantsDuplicates stronger ideas around surface-named pages, summaries, Cornell containment, and preview contracts.

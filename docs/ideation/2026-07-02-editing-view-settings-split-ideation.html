Editing View Settings Split

A fresh ideation pass on splitting settings so Cornell View styling has its own named destination, while settings that only affect the live editor move into a new Editing View page. The product reason is strategic: Cornell View may eventually be removed as an extra step with limited benefit, so Editing View appearance may become CueCraft's main study surface.

Date: 2026-07-02 Updated: 2026-07-03 Topic: editing-view-settings-split Focus: rename Appearance to Cornell View and add Editing View settings with Editing View as a possible future primary surface Mode: repo-grounded
Grounding Axes 1. Split 2. Editing View 3. Cross-view toggles 4. Summaries 5. Tests 6. Future Reading View Rejected

Grounding Context

  • CueCraft is an Obsidian plugin for active-recall study cues. The README distinguishes Editor-mode cue questions from a dedicated Cornell view, and separately calls out Cornell view styles in settings.
  • The settings home currently has a single Appearance nav card whose description says it adjusts Cornell view styling, sizing, accents, and compact display options.
  • The Appearance subpage header says "Cornell view styling, layout, cue accents, and visual density," but the first two controls in renderAppearanceSection are Editor cue display and Rail card background.
  • The current appearanceSummary() mixes editor state and Cornell state in one string: editor display, hook card style, Cornell display mode, Cornell style, width, and font size.
  • Note format currently contains Reading mode controls, cross-view review-surface toggles, editor rail-only toggles, and one Cornell mobile toggle. That makes the page a grab bag rather than a semantic destination.
  • The strategic premise changed after the first draft: Cornell View may be removed in the future because it adds an extra user step with limited benefit. That makes Editing View appearance work more important, because the editor may become the main review surface.
  • Behavioral evidence is cleanly separable: editor rail settings call refreshEditorCues(); Cornell appearance settings call refreshCornellViews(); review-surface toggles refresh editor, Reading mode, and Cornell view together.
  • No settings data migration is required. The split is about page taxonomy and rendering placement, not changing stored setting keys.

Ranked Ideas

1

Make Cornell View the renamed, Cornell-only Appearance page

Axis: Navigation naming Confidence: 94% Complexity: Low

Description: Rename the existing Appearance subpage, nav card, heading, and summary to Cornell View. Its controls should be only settings whose visible effect is the Cornell pane: display mode, Cornell style, cue column width, cue font size, accent, border, compact supports, and mobile folding.

Basisdirect: src/settings.ts:291-297 renders the current Appearance page with a Cornell-specific description, while src/settings.ts:1263-1407 contains both editor controls and Cornell controls.
RationaleThe user's requested rename becomes truthful instead of cosmetic: the page label, description, summary, and contents all point at the same surface.
DownsidesExisting users who remember "Appearance" need one release cycle to re-map the label, but the new name is more precise.
Meeting TestThis warrants team discussion because it sets the durable information architecture for every future visual setting.
2

Add an Editing View page for editor-only visual controls and future main-surface polish

Axis: Editing View-only controls Confidence: 91% Complexity: Medium

Description: Add editing-view as a settings subpage and home nav card. Move Editor cue display, Rail card background, Show rail questions, and Show rail support terms there because those controls only affect CodeMirror/editor rail rendering. Treat this page as the first home for editor appearance polish, not just a relocation bucket, because Editing View may become CueCraft's main review surface if Cornell View is retired.

Basisdirect: src/settings.ts:1271-1303 saves editor display and rail card style by refreshing editor cues, and src/settings.ts:1217-1239 does the same for rail questions and rail support terms. reasoned: if Cornell View may be removed because it adds an extra step, the editor-only display controls are no longer secondary polish; they shape the likely primary review experience.
RationaleThe new page answers the user's exact rule: settings that only affect Editing View should live under Editing View, regardless of whether they are currently in Appearance or Note format. It also gives future editor-first design work a clear destination before Cornell View decisions are final.
DownsidesThe settings home gains one more card. That is acceptable because it removes ambiguity rather than adding a feature.
Meeting TestThis is the central product move and should be the first implementation slice because it improves the surface most likely to matter if Cornell View is removed.
3

Keep cross-view review toggles out of Editing View

Axis: Cross-view review toggles Confidence: 88% Complexity: Low

Description: Do not move Show Section Lens or Show Note Brief into Editing View. They may be rendered in the editor, but they are not editor-only: they affect Reading mode and Cornell/review surfaces too. Keep them in Note format, or rename that remaining page later to Review Surfaces.

Basisdirect: src/settings.ts:1191-1214 toggles Section Lens and Note Brief through refreshReviewSurfaces(); src/settings.ts:1256-1259 refreshes editor, Reading mode, and Cornell views together.
RationaleThis preserves the user's boundary. "Editing View" should not become the new catch-all for anything visible while editing.
DownsidesUsers may still wonder why "Note format" contains display settings. That is a separate naming problem, not part of the Editing View split.
Meeting TestImportant because it prevents the split from introducing a new misleading bucket.
4

Split the mixed Appearance summary into Cornell and Editing summaries

Axis: Navigation naming Confidence: 84% Complexity: Low

Description: Replace appearanceSummary() with cornellViewSummary() and add editingViewSummary(). The Cornell card can summarize Cornell mode, style, width, and font size; the Editing View card can summarize editor display, rail background, and rail content visibility.

Basisdirect: src/settings.ts:461-475 currently returns a single summary string that mixes editor display, hook card style, Cornell display mode, Cornell style, width, and font size.
RationaleThe nav cards are the user's first orientation point. If their summaries mix surfaces, the split feels incomplete even if the subpages are right.
DownsidesSmall duplication risk in summary formatting. Keep each summary inline and simple rather than adding a generic summary abstraction.
Meeting TestWorth doing with the split because it is a low-cost correctness detail users will notice.
5

Verify the split by refresh behavior, not just labels

Axis: Refresh and verification behavior Confidence: 79% Complexity: Medium

Description: Add focused tests or review checks that classify moved settings by their refresh path. Editing View controls should save and call refreshEditorCues(); Cornell View controls should save and call refreshCornellViews(); review toggles should still refresh all review surfaces.

Basisdirect: src/main.ts:399-405 passes editor display, rail questions, rail support terms, and hook card style into the editor render payload; src/settings.ts:1405-1407 refreshes Cornell views for Cornell appearance changes.
RationaleTests anchored to behavior catch the subtle regression where a setting is placed under the right label but still refreshes the wrong surface.
DownsidesCurrent tests mostly validate defaults and enum validity, so DOM-level settings tests may need lightweight harness work.
Meeting TestStrong because this is the difference between a rename and a reliable settings taxonomy.
6

Leave room for a later Reading View page without doing it now

Axis: Cross-view review toggles Confidence: 72% Complexity: Low now, Medium later

Description: Keep Reading mode controls in Note format for this slice, but name the code so a future Reading View split is obvious. The current request is specifically about Editing View-only settings, so moving Reading mode now would broaden scope.

Basisdirect: src/settings.ts:1156-1189 contains Reading mode visibility and display controls, while the user specifically asked for a new page for changes that affect Editing View and not Cornell View.
RationaleThis keeps the implementation small and respects the user's requested boundary, while avoiding code names that make the next split harder.
DownsidesThe leftover Note format page remains imperfect until a later Reading/review settings cleanup.
Meeting TestUseful as a scope guard rather than a feature commitment.

Rejection Summary

# Idea Reason Rejected
1 Rename Note format to Editing View Scope mismatch: Reading mode, Section Lens, Note Brief, and Cornell mobile folding are not Editing View-only.
2 Keep one Appearance page with Cornell and Editing sections Violates the user's explicit ask for a new Editing View settings page and preserves the ambiguous top-level label.
3 Duplicate rail controls in both Note format and Editing View Creates two places to change one setting; Obsidian settings should avoid duplicated controls with shared persistence.
4 Rename stored settings keys to match page names Too expensive relative to value. The user asked for settings page organization, not a persistence migration.
5 Move Section Lens and Note Brief into Cue generation Partly plausible, but README says turning those displays off does not stop generation. They are display toggles, not generation controls.
6 Create a full Settings IA redesign Scope overrun. The current change can be surgical and should not reopen AI Provider, Study Areas, or Study Mode.

Easier AI provider configuration

A grounded exploration of how FirstRecall can replace a dizzying 15-brand wall with choices new AI users can understand—without hiding providers or implying a preferred vendor.

Point of view: split the providers, but do not lead with the infrastructure labels “Cloud / CLI / Local.” Lead with three equal-weight connection paths—Use an API key, Use an installed AI tool, and Use a model server—then explain the technical category.

What users see now

One accessible 15-option radio grid gives every brand the same visual weight. A tile shows icon, name, and selection state—but no prerequisite, billing distinction, model requirement, or connection type.

What the code already knows

Central provider metadata encodes three credential contracts: API key, URL, and command. It also knows model requirements, listing behavior, labels, descriptions, and provider help links.

Where setup becomes difficult

Users choose a brand before seeing whether it needs separate API access and billing, a running local server, or an installed and authenticated desktop tool.

Where leverage exists

The picker and selected-provider setup panel are centralized, and settings persist per provider. The information architecture can change without changing runtime provider behavior.

External evidence

VS Code separates everyday model choice from model-provider management. Open WebUI distinguishes cloud providers from local servers before connection details. Choice-architecture research favors concise classification and sequencing when alternatives differ across several attributes, provided users can still reach every option.

I1. Guided connection paths

Rank 1 · Top pick

Description: Replace the first 15-way brand decision with three equal-weight paths: Online service — use an API key; Installed AI tool — use Codex or Claude already installed; and Model server — use Ollama or LM Studio. Each path reveals every matching provider in stable order. A persistent Browse all providers escape prevents the paths from becoming hidden defaults. On a clean install, the prompt can be phrased as “What do you already have?”

Axis
Catalog organization + first-run guidance
Confidence
93%
Complexity
Medium

Basis

direct: src/byok-provider-metadata.ts already defines 11 API-key, two command, and two URL providers; README.md already explains Cloud APIs, Desktop CLIs, and Local servers. external: Open WebUI similarly separates hosted APIs and local servers before connection details.

Rationale

The user’s grouping instinct is right, but “CLI” is a technical implementation label and a vertical Cloud-first list can still feel like a recommendation. Equal-weight, plain-language paths ask a question novices can answer from what they possess.

Downsides

Adds one navigation decision before a provider. The path labels must clarify that installed CLI tools may still use online services, while custom model-server URLs are not guaranteed to be on-device.

I2. Provider “what you’ll need” labels

Rank 2

Description: Add a standardized compact contract to every provider before selection: what credential or software is needed, whether model selection is required, and whether cloud API access can involve separate billing from consumer subscriptions. The same facts should carry into the selected setup panel so preview and setup do not drift.

Axis
Setup comprehension
Confidence
84%
Complexity
Low

Basis

direct: Provider metadata already contains credential kind, credential description, help URL, model behavior, and listing support. docs/cloud-api-keys.md documents that API access is separate from consumer subscriptions and may require billing or credits.

Rationale

The easiest catalog to scan is one where unfamiliar brands are still operationally legible. Repeated fields work like a nutrition label: users compare the same facts in the same order.

Downsides

More copy can make tiles noisier. Provider-level privacy claims are not uniformly supportable: an editable “local” URL might point elsewhere, and installed CLIs may call online services. Keep those claims precise and category-level.

I3. Your connections / Add a connection

Rank 3

Description: Treat first use and repeat use as different jobs. A clean installation opens to the guided paths. After one or more providers are configured, the page leads with Your connections: provider, saved model or default, and verified, stale, or untested status. The complete catalog stays directly available under Add a connection. Everyday Use now switching is distinct from managing credentials and tests.

Axis
Returning-user efficiency
Confidence
91%
Complexity
High

Basis

direct: FirstRecall already persists credentials, models, fetched options, and verification state separately per provider. external: VS Code separates everyday model selection from the Language Models management surface.

Rationale

No fixed Cloud / CLI / Local order serves both a clean install and a mature setup. Lifecycle state is a stronger repeat-use signal than provider category: known connections should lead only after the user creates them.

Downsides

This is a larger information-architecture shift than adding group headings. “Configured,” “verified,” and “active” must remain visually and semantically distinct.

I4. Pair before activating

Rank 4

Description: Opening a provider begins inspection and configuration; it does not immediately replace the active provider. A separate Use this provider action activates the connection after setup, analogous to pairing a device before selecting it as the active output.

Axis
First-run guidance + returning-user efficiency
Confidence
90%
Complexity
Medium

Basis

direct: Clicking a provider currently writes selectedProvider immediately, and that same value drives generation. The repository already keeps per-provider records, so editing an inactive provider has a credible state foundation.

Rationale

Browsing should not carry a hidden operational commitment. This lets novices compare setup paths and lets experienced users prepare a backup without displacing a known-good provider.

Downsides

Introduces another state and action. The interface must make active, configured, incomplete, and merely inspected states unmistakable.

I5. Provider-aware setup checklist

Rank 5

Description: Present the selected setup as visible status-bearing steps: connect with a key, URL, or command; choose a model when required; then test. Focus the next incomplete action, mark CLI model override as optional, and move directly into model selection after a successful connection instead of making users rediscover a fetch control.

Axis
Setup comprehension
Confidence
92%
Complexity
Medium

Basis

direct: The current panel already renders credentials, model, then setup status and computes missing, saved, selected, verified, stale, and untested states. The cloud test flow already fetches models when none is selected.

Rationale

The controls already have an order; exposing it turns hidden dependencies into one coherent route to “ready to generate.”

Downsides

A universal-looking checklist can misrepresent provider differences. Local servers require models, while CLI model overrides are optional; the steps must render from each provider contract.

I6. Check this computer

Rank 6

Description: Offer an explicit availability check for Ollama, LM Studio, Codex CLI, and Claude CLI using the existing default endpoints and command names. Report factual signals such as “Ollama endpoint reachable” or “Codex command found,” never silently select a provider, and retain manual custom URL or command setup.

Axis
First-run guidance
Confidence
86%
Complexity
Medium

Basis

direct: FirstRecall already has default localhost endpoints and command names, and the installed runtime can check endpoint reachability and executable presence without launching the CLIs.

Rationale

Users who already installed a supported tool should be able to begin from what demonstrably exists on their computer instead of understanding URLs and commands first.

Downsides

Detection is not authentication or complete readiness. The copy must avoid overstating “command found” as “ready,” and custom paths remain a separate case.

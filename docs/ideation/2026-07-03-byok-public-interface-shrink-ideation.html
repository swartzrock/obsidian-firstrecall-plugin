CueCraft codebase BYOK public API 2026-07-03 Continuation of BYOK simplification

Make CueCraft Use BYOK Like A Customer, Then Shrink BYOK Like A Library

The strongest direction is to stop letting CueCraft consume every BYOK helper through the public barrel. CueCraft should use the same small public generation/model-listing/provider enum API that external apps see, while CueCraft-specific settings, model-combobox, Anthropic picker, verification, and storage helpers move behind an app adapter or internal subpath.

Grounding Context

What CueCraft Uses Today

src/byok-cuecraft-adapter.ts imports BYOK registry helpers, setup-state helpers, Anthropic normalization, fetched-model sorting, provider errors, runtime types, and provider storage types. It creates runtime providers via createByokNodeProvider, not createByokProvider directly.

src/settings.ts imports many BYOK UI/model helpers directly, including Anthropic-specific UI affordances and generic model normalization. Settings also refreshes models through the runtime provider.listModels() path rather than the new top-level listModels(options) helper.

Public Surface Tension

The public barrel currently exports a broad toolkit: simple helpers, provider factory, registry metadata, Anthropic UI helpers, setup-state storage helpers, model sorting utilities, error classes, provider runtime interfaces, and many app-shaped setting types. This makes extraction easier for CueCraft but makes the standalone library feel larger than the README promise.

The AI SDK docs model the opposite posture: a tiny default verb such as generateText with advanced areas discoverable separately. BYOK does not need to copy the exact API, but it should copy that shape: small front door, explicit advanced doors.

Topic axes: public generation API; model discovery/setup API; CueCraft integration boundary; provider registry/metadata; low-level helper exports.

Ranked Ideas

1Split BYOK Into Three Audiences

Create a strict public main entrypoint for external users, a Node entrypoint for CLI/local command runtimes, and a CueCraft-owned adapter layer for settings/storage/UI helpers. The main barrel should feel like a small SDK, not the entire BYOK implementation toolbox.

Shape
@cuecraft/byok: ByokProvider, generateText, createByok, listModels, core config/result types, model option type, public errors. @cuecraft/byok/node: createByokNodeProvider and node-only config/types. CueCraft app code owns or imports from an internal adapter for registry/settings helpers.
Basis
direct: CueCraft imports many non-generation helpers from the BYOK barrel, while README quick start now emphasizes simple function-first calls.
Why It Matters
This makes CueCraft dogfood the public API for generation while preventing CueCraft settings needs from bloating the public library contract.
Confidence
High. This directly resolves the user's stated goal and matches the already-emerging README direction.
Complexity
Medium. Requires import migration and public-contract test reshaping, but not provider behavior rewrites.

2Make CueCraft Refresh Models Through listModels(options)

Settings should stop constructing a runtime just to list models. It should resolve provider credentials from CueCraft storage, then call the public listModels helper with ByokProvider enum values. Runtime provider.listModels() can remain internal or advanced.

Shape
refreshProviderModels and the Anthropic refresh path would build a model-list config and call listModels({ provider: ByokProvider.OpenAI, apiKey }) or listModels({ provider: ByokProvider.Ollama, host }).
Basis
direct: settings.ts currently asks provider.listModels() after makeProvider(); earlier interface work added top-level model-free listModels exactly to avoid requiring a selected model.
Why It Matters
CueCraft would validate the simplest setup-time public API in production code and catch docs/API drift earlier.
Confidence
High.
Complexity
Small to Medium, depending on how credential-store resolution is threaded into settings.

3Move Anthropic Picker Helpers Out Of The BYOK Public Barrel

The Anthropic custom-model picker is CueCraft UI policy, not generic BYOK provider access. Keep the provider model-list implementation in BYOK, but move ANTHROPIC_CUSTOM_MODEL_ID, model hints, unavailable-message copy, and custom-selection normalization into CueCraft or a non-public/internal package path.

Basis
direct: settings.ts consumes Anthropic helpers for dropdown presentation and custom-model UI. These helpers are provider-specific and subjective: quality/speed/cost/context labels are CueCraft UX, not a universal BYOK SDK promise.
Why It Matters
Removing these from the main barrel shrinks the API and avoids locking a public library into CueCraft's Anthropic UX language.
Confidence
High.
Complexity
Small. Mostly file moves/import changes and contract test updates.

4Replace Public Setup-State Helpers With CueCraft-Owned Settings Logic

deriveProviderSetupStatus, recordProviderConnectionSuccess, providerCredentialFingerprint, ByokStoredSettings, and ByokProviderStoredSettings make BYOK look like it owns app storage. CueCraft does need this logic, but a standalone BYOK library should not imply a blessed settings schema.

Basis
direct: byok-cuecraft-adapter.ts wraps these helpers to derive setup state and record verification snapshots. The README also says host apps own storage schema, encryption, and migration flow, which conflicts with exporting BYOK storage types as first-class public API.
Why It Matters
This is the cleanest way to make BYOK app-agnostic. External apps can store whatever they want and pass credentials at call time.
Confidence
Medium High.
Complexity
Medium. CueCraft must retain equivalent logic locally or in a CueCraft integration module.

5Turn Provider Metadata Into A Minimal Public Function, Not A Full Settings Schema

Keep enough provider metadata for external apps to build a picker, but remove fields that encode CueCraft's settings UI. A public providers() result should likely include id, label, credentialKind, supportsModelListing, supportsLocalExecution, and maybe requiresNetwork. Placeholders, missing-message copy, icon SVGs, model-field descriptions, and reset messages should become CueCraft integration data.

Basis
direct: ByokProviderDefinition currently includes labels, product labels, vendor labels, icon definitions, credential-field copy, model-field copy, model behavior, and capability flags.
Why It Matters
Provider metadata is useful, but UI copy and icons create subjective public API commitments. A small metadata contract is easier to support after extraction.
Confidence
Medium.
Complexity
Medium because settings UI depends on the richer shape.

6Demote createByokProvider() From Public Main Path To Advanced/Node-Or-Internal

CueCraft does not import createByokProvider directly. It imports createByokNodeProvider, which delegates non-CLI providers to the core factory internally. That suggests the external public story should not start with the runtime factory. Keep it only if structured output and connection testing cannot be covered by smaller public verbs.

Basis
direct: makeCueCraftByokProvider calls createByokNodeProvider; createByokNodeProvider delegates default cases to createByokProvider. The README already now leads with generateText and listModels.
Why It Matters
A public runtime factory invites callers into optional methods, provider-specific hints, object generation, and custom deps before they need them.
Confidence
Medium. It may still be valuable for advanced apps, but should not be part of the small mental model.
Complexity
Small if docs-only; Medium if removed from the main barrel.

Rejected Or Deferred Ideas

IdeaReason Cut
Remove generateObject() immediatelyCueCraft currently uses it for cues, summaries, and note briefs when available. Removing it now creates behavior risk; demote docs first, then consider a text+schema replacement later.
Expose only AI SDK-compatible model objectsBYOK's point is provider account access with local providers and CLI support; copying AI SDK exactly would erase BYOK's reason to exist.
Make every CueCraft setting screen call public generateTextGeneration is not the main setup-screen need. Model listing, connection testing, and local CLI providers need separate paths.
Remove all provider metadataSome metadata is valuable for provider pickers and validation. The problem is the breadth and CueCraft-specific UI copy, not the existence of metadata.
Hide all types except inferred optionsTypeScript library consumers need named config/result types for wrappers, factories, tests, and app boundaries. Shrink the type surface, but do not make it opaque.

This is intentionally not an exact implementation plan. The next step should decide whether CueCraft-only helpers move into src/byok-cuecraft-adapter.ts, a package-internal path, or a clearly non-public subpath such as @cuecraft/byok/cuecraft that will not ship in the standalone open-source repo.

Implementation Sequence To Explore Next

  1. Change CueCraft code to import and use ByokProvider enum values for provider-specific logic.
  2. Change settings model refresh flows to call top-level listModels(options) for cloud and Ollama providers.
  3. Move Anthropic picker helpers and provider-field UI copy into CueCraft-owned code.
  4. Move setup-state/storage helpers into CueCraft-owned code, leaving BYOK credential-agnostic.
  5. Shrink packages/byok/src/index.ts and public-contract tests to the small main barrel.
  6. Keep provider runtime factories available only where needed: node entrypoint and possibly an advanced/internal export.

External Reference

Vercel's AI SDK documentation presents a compact front door around generateText, while deeper concepts such as providers, structured data, tools, and telemetry sit behind separate docs sections. BYOK should borrow that information architecture even if it keeps BYOK-specific provider enum and credential options.

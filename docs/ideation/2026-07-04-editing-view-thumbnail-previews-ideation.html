Editing View thumbnail previews

Fresh design directions for replacing the Editor cue display and Rail card background dropdowns with preview buttons that show what changes in the Editing View, not in Cornell View.

Grounding Context

Polish direction: use the Cornell View Style thumbnail language for the outer control: compact white option cards, a paper-like preview pane, concise bold labels, muted two-line descriptions, and a bright selected border. The preview art inside each card should stay editor-specific and should be treated as a design target, not as code-ready mockup art.

Current shape

The Editing View page already owns editor-only display settings. Width and font have thumbnail previews, while display mode and rail-card background are still dropdowns.

Available options

  • Six display modes from EDITOR_CUE_DISPLAY_OPTIONS.
  • Two background styles from EDITOR_HOOK_CARD_STYLE_OPTIONS.
  • One shared thumbnail button renderer already used elsewhere.

Design pressure

Editing View may become the main review surface later, so these previews should make editor behavior legible on its own instead of borrowing Cornell View metaphors.

Topic Axes

Display placementDoes the preview show where the cue appears relative to note text?
Background materialDoes the preview isolate the difference between classic and gradient rail cards?
Active section stateDoes the thumbnail clarify current, upcoming, or collapsed behavior?
Settings densityDoes the design survive narrow panes and Obsidian settings layout constraints?

Ranked Ideas

The top recommendation is to use editor-truth display miniatures, then handle rail-card background as material swatches on a shared card. The other survivors are useful variants or follow-ups.

1. Editor-Truth Miniatures 2. Rail Material Swatches 3. Current-Section Ladder 4. Compact Anatomy Icons 5. Optional Paired Preview Row
1

Editor-Truth Miniatures

Render each Editor cue display choice as a Cornell-style thumbnail card containing a tiny CodeMirror-like preview pane: note text on the left, cue affordance in the exact place the mode uses. The thumbnail is not a decorative card; it is a polished placement model.

Axis: display placement Confidence 92% Complexity Medium

Basis: direct: src/editor-cue-display.ts names six distinct editor surfaces, and src/settings.ts currently hides them behind a dropdown. The existing Cornell View Style thumbnails establish the interaction style: visible preview first, bold option name, short muted explanation, and selected-state emphasis. NN/G's recognition-over-recall heuristic also supports making option effects visible at decision time.

Rationale Users should compare placement, not memorize labels like "threaded margin notes" or "hook minimap."
Downside Requires six preview recipes and visual tuning; the sketches below are style direction only, not final art to copy verbatim.

2

Rail Material Swatches on One Anchored Card

For Rail card background, use two thumbnails that share the same anchored-card structure and change only the material treatment. This makes "Classic warm/cool" versus "Soft gradients" immediately visible without implying that the display mode changes.

Axis: background material Confidence 90% Complexity Low

Basis: direct: src/editor-hook-card-style.ts has only two style values, both descriptions about rail card appearance. The preview should therefore be a material comparison, not six display-mode permutations.

Rationale The user can evaluate color/finish in one glance, and implementation can reuse one preview helper with a style modifier.
Downside It previews background most truthfully for rail/card modes, while inline cues are less affected.

3

Current-Section Ladder

Use the same three-section note scaffold across every display thumbnail, with the middle section visibly active. This makes current-section behavior comparable across composer, minimap, tabs, and rail displays.

Axis: active section state Confidence 84% Complexity Medium

Basis: reasoned: editor cue modes differ partly by whether they foreground the active section, collapse inactive sections, or show nearby hooks. A constant scaffold lets the viewer compare that behavior instead of comparing six unrelated pictures.

Rationale Especially helpful for active-section-composer and hook-minimap, whose value is about focus.
Downside Slightly more abstract than the top choice; it may need one or two labels inside the preview.
Design sketchShared scaffold
4

Compact Anatomy Icons

Offer a denser fallback recipe for narrow settings panes: a simple note-line glyph plus cue placement mark for each display option. The labels do more of the work; the icon only disambiguates placement.

Axis: settings density Confidence 78% Complexity Low

Basis: direct: existing thumbnail CSS uses auto-fit grids with relatively small card widths. Some users will see these controls in narrow Obsidian settings panes, where detailed scenes can become cramped.

Rationale Keeps previews legible when the full editor-scene recipe compresses too far.
Downside Less emotionally satisfying than full thumbnails; better as responsive fallback than primary desktop design.
Design sketchAnatomy set
5

Optional Paired Preview Row

After the two thumbnail groups, show one small read-only row that combines the currently selected display mode with the selected rail-card background. This is not a full live preview panel; it is a sanity check for how the two choices interact.

Axis: combined choice Confidence 70% Complexity Medium

Basis: reasoned: users may wonder whether the background style applies to every display option. A compact combined preview can answer that without adding a large settings-page preview surface.

Rationale Helps with edge cases such as inline cues, where rail-card background is less visually central.
Downside Adds one more element to the settings page; should wait until the two thumbnail groups feel insufficient.

Rejection Summary

# Idea Reason Rejected
1 Animated hover preview Interesting but too much motion for a settings affordance; it risks hiding the important information until hover and adds accessibility cost.
2 Full settings page live preview Useful as a later polish pass, but too heavy for this specific ask to replace two dropdowns with thumbnail previews.
3 Screenshot-based thumbnails Brittle across themes, pane widths, and font scaling; code-drawn thumbnails will be more maintainable inside an Obsidian plugin.
4 Cornell-style thumbnails reused for Editing View Scope mismatch: the user explicitly wants editor-only previews, and prior settings-split work identified Cornell miniatures as misleading for editor behavior.

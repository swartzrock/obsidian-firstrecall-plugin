System instructions for note summaries

The new channel is useful as a configurable study-review rubric, not as a second copy of the whole prompt. The strongest direction combines a persisted user override with a safe built-in default, while a fixed, self-contained user prompt keeps the immediate command after the note.

What the candidates had to survive

Grounding Context

Current prompt shape

Cuecraft's summary request currently combines stable study-review rules, JSON instructions, the note title, successful section questions, and clamped whole-note markdown in one user prompt. The prompt ends with the note text.

Runtime parity

byok-runtime 2.3.0 accepts instructions on both generateText and generateObject. Cuecraft can now send the same summary rubric through the preferred structured-object route and text fallbacks.

Reliability gap

The current schema proves that summary is a nonblank string. It does not enforce one-sentence form, faithfulness, cross-section synthesis, or usefulness as a study takeaway.

Settings fit

Cuecraft already persists global generation settings, exposes a dedicated Cue generation subpage, and marks generation-affecting changes so existing notes can be regenerated. A summary-policy override fits that established lifecycle.

External evidence

OpenAI, Anthropic, and Google converge on separating persistent behavior from per-call task and context. Google also recommends placing the concrete task close to the end for long documents.

Decision-changing fact

Store a user's customization as an override, not a copied snapshot of today's default. With no override—or after “Reset to default”—Cuecraft should resolve the latest built-in rubric. The portable prompt still retains the JSON contract and final command so the system rubric remains focused on study-review judgment rather than transport details.

1. Configurable two-layer summary prompt

Top pickConfidence · 89%Complexity · Medium

Add a multiline “Summary system prompt” control under Cue generation settings. Cuecraft resolves its effective rubric from a persisted user override when present, otherwise from the current built-in default; “Reset to default” clears the override. Send that effective rubric as text-route instructions on both initial and repair requests. Separately, keep the exact artifact, JSON keys, sentence limit, title, section questions, note text, and a fixed end-of-note command in the portable user prompt used by every route.

The user may customize Cuecraft's study-review judgment without owning the transport contract. Version 2.3.0 carries the effective rubric through both object and text generation, while the fixed portable prompt remains sufficient on its own.

Axis
Prompt responsibility
Basis
direct: Cuecraft already saves global CueCraftSettings, has a Cue generation settings page, and marks generation-affecting changes for regeneration. byok-runtime 2.3.0 maps instructions to native system/developer channels for both text and structured-object generation.
Rationale
This gives advanced users meaningful control, keeps future default improvements available to everyone who has not customized the rubric, and preserves one provider-neutral artifact contract. The fixed end command also places the concrete task closest to generation on long notes.
Downsides
A conflicting or weak override can reduce summary quality, and the setting needs clear “Built-in default” versus “Customized” state. Default, override, blank-value, reset, initial-request, and repair-request behavior all need tests.

3. Summary-specific semantic acceptance gate

Confidence · 78%Complexity · Medium

Treat a generated summary as a candidate until it passes narrow, explainable checks: one-sentence form, concise length, avoidance of generic filler, and an observable relationship to supplied note or cue concepts. A failed criterion becomes a targeted repair instruction rather than a generic “try again.”

Axis
Semantic adherence
Basis
direct: Cuecraft's summary schema accepts any trimmed, nonblank string. Sentence count, grounding, and usefulness live only in descriptions and prompt prose. Google's structured-output guidance likewise distinguishes schema adherence from semantic correctness.
Rationale
A system prompt can influence behavior, but only an acceptance loop can detect the polished-yet-useless summary that currently counts as success.
Downsides
Grounding checks can become brittle or reward keyword overlap. Begin with objective properties and a small rubric before attempting deeper semantic scoring.

4. Metamorphic provider-conformance lab

Confidence · 88%Complexity · Medium

Keep representative notes fixed and vary only the channel arrangement: inline-only, system/user split, and split plus end reminder. Across object, text/cloud, Ollama, Claude CLI, and Codex CLI routes, measure sentence compliance, note specificity, section-question alignment, JSON success, repair rate, token cost, and native instruction placement.

Axis
Testability and maintenance
Basis
direct: The repo already defines a five-note manual evaluation shape and a “whole-note takeaway, not another section cue” criterion, but has no summary-prompt rubric, golden fixture set, provider matrix, or prompt-placement assertions.
Rationale
This changes “system prompts should work better” from generic prompt-engineering intuition into repeatable evidence about Cuecraft's artifacts and provider mix.
Downsides
Live-model results are nondeterministic and cost-bearing. The corpus and scoring rubric must stay small enough to remain usable during prompt changes.

5. Capability-conformance envelope

Confidence · 86%Complexity · Medium

Define one end-to-end summary request contract—persistent behavior, task and source context, structured artifact, semantic checks, and repair behavior—and document how each runtime route satisfies it. Transport differences become explicit without allowing the intended output to fork by provider.

Axis
Runtime/provider reach
Basis
reasoned: A must-have stored only in a transport channel unavailable to the preferred route cannot be a Cuecraft invariant. A route-neutral contract exposes that gap and makes future provider additions acceptance questions rather than fresh prompt-design decisions.
Rationale
It gives Cuecraft a durable boundary between semantic intent and provider-specific encoding, while remaining smaller than a general prompt framework.
Downsides
If expressed as a new abstraction before tests exist, it can become architecture without leverage. Start as a documented contract and route-level assertions.

6. Persist the invariant policy during repair

Confidence · 89%Complexity · Low

Send the same study-summary instructions on both the initial text request and its JSON repair request. Let the repair user message focus on the parse or validation failure while the higher-level channel continues to enforce grounding, concision, and study purpose.

Axis
Semantic adherence
Basis
direct: Cuecraft's text path makes one repair request after validation failure, but neither the initial nor repair summary call currently includes instructions. Repair is precisely where a formatting task can displace the original semantic purpose.
Rationale
It closes a concrete inconsistency with very little surface area and makes the system rubric useful in the failure state where persistence matters most.
Downsides
It helps only text routes and cannot repair semantically poor but schema-valid output without survivor 3's acceptance criteria.

Ideation: Cue Card Rail Hierarchy

A focused idea set for making anchored cue cards line up with note content and read in the desired order: question first, terms second.

Date: 2026-07-08 Topic: cue-card-rail-hierarchy Mode: repo-grounded Focus: anchored cue-card polish

Grounding Context

  • CueCraft renders active-recall cues as a non-destructive study layer beside Markdown notes. The README frames the core scan path as seeing a question, attempting recall, then checking source and summary.
  • The current implementation is the editor hook rail: src/cue-extension.ts renders anchored rail cards through renderEditorHookElement(), and src/editor-hook-rail.ts provides card data.
  • CueLineData.line is documented as the heading line, populated from Section.lineNumber, then used by buildCueGutterMarkers() to place gutter cards at headingLine.from.
  • The anchored-card DOM already matches part of the reference direction: no visible category tag, no Section Lens in the card, labels for QUESTION and TERMS, question title, and keyword chips.
  • styles.css makes cards compact with max-width: min(16.75rem, 100%), scoped card tokens, a divider before non-first section labels, and density-specific title overrides.
  • Prior July 6 plans already name this direction as "question, divider, and terms." The new work is therefore a precise visual hierarchy and placement pass, not a new product surface.

1. Reading-order rail card

Anchor relationshipConf 88%Cx M
Description
Treat the requested changes as one cohesive rail-card reading-order slice: align the card with the first body text under the heading, make the question the only strong text in the card, then show at most four quiet terms below a divider with an explicit reveal for overflow.
Basis
direct: the user-provided design shows the card top aligned with the first explanatory line under the heading, while the current screenshot shows the card visually tied too high. The repo backs this up: buildCueGutterMarkers() places cards at the heading line.
Rationale
This preserves CueCraft's retention-first scan path. The user sees the note heading, the note body starts, and the cue card begins at the same vertical rhythm as the answer material it is prompting.
Downsides
The anchoring part needs care around headings with no body text, wrapped headings, and narrow panes. It should be verified visually, not only with unit tests.

2. Question focal block

Question hierarchyConf 90%Cx L
Description
Scope anchored-card rail CSS so the question text lands around 15-16px, semibold, with a slightly calmer label above it. Put the thin divider directly after the question block so the card reads as one primary prompt followed by secondary supports.
Basis
direct: current CSS gives .cuecraft-editor-hook-title semibold weight but relies on inherited or density-reduced sizing. The user's desired hierarchy explicitly says the QUESTION text should be the card focal point.
Rationale
This is the highest value, lowest risk part of the request. It makes the card pass the squint test: question first, labels and terms second.
Downsides
Long generated questions may wrap more. The existing density classes should continue to trim line-height or size for dense titles instead of letting tall cards break the rail.

3. Four-chip terms with +N more

Term overflowConf 82%Cx M
Description
Add an anchored-card-specific term presentation that renders the first four chips, then a small muted +N more button when extra terms exist. Expanding should reveal the hidden chips in place without changing note content or provider/cache data.
Basis
direct: the current renderer sends all card.keywords through appendCueTerms(). The user's request asks to cap visible terms at four with a toggle.
Rationale
Term chips are useful hints, but too many compete with the question. A visible cap makes the desired priority durable even when generation returns five or more keywords.
Downsides
This is the only survivor that adds interaction. It needs an accessible button label and should not cause rail layout jitter when toggled.

4. Anchored-card-only placement change

Anchor relationshipConf 78%Cx M
Description
If implementation changes marker placement, apply it only to anchored-card-rail. Keep collapsed tabs, minimap, active composer, and Cornell fallback behavior attached to the existing heading-line contract unless a separate design request says otherwise.
Basis
direct: tests currently assert hook displays render into gutter markers at heading lines. The user request and screenshots are specifically about cue cards, not every hook display.
Rationale
This keeps the change surgical. Other displays may depend on heading-line anchoring as an intentional affordance, while the rail card is the one whose rectangle should visually align to body text.
Downsides
A display-specific marker target may require a small helper to avoid sprinkling display checks through placement code.

5. Focused DOM and CSS regression pins

Regression safetyConf 85%Cx L
Description
Update the existing focused tests instead of adding a new suite: assert the anchored card still renders QUESTION and TERMS, assert the term cap/toggle behavior, assert the title sizing/weight/divider CSS, and adjust marker-position tests only for anchored-card rail if placement changes.
Basis
direct: tests/cue-extension.test.ts already covers anchored-card DOM and marker positions, while tests/settings-css.test.ts already checks compact rail card CSS.
Rationale
The request is visual, but this repo already guards visual contracts through DOM/CSS text tests. Extending those pins keeps the change small and traceable.
Downsides
CSS tests cannot prove real pixel alignment. A manual screenshot pass in Obsidian is still needed after automated checks pass.

Rejection Summary

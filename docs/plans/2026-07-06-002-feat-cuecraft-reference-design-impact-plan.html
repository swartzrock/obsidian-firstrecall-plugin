Goal Capsule

Objective

Explain the impact of proposed changes 1-7 so a later implementation pass can preserve the reference design's hierarchy, restraint, and markdown-native feel.

Product Authority

The source of truth is the user's original visual reference, plus the follow-up review notes about icons, term chips, dividers, Note Brief section rules, and the limits of cue.category.

Open Blockers

The only product decision that may block planning is whether heading-side chips should exist without a new domain-neutral primary term field.

Product Contract

Summary

Bring the redesign closer to the reference without making CueCraft feel like a dashboard.

The proposed changes make Note Brief more editorial, make anchored cue cards narrower and calmer, and keep generated metadata visually subordinate to the user's note. The design should read as enhanced markdown with study scaffolding, not as a separate web app sitting on top of Obsidian.

Problem Frame

The current redesign is close, but several details still compete with the note.

The first redesign pass established the unified card system and removed the loud pastel fills. The remaining gap is hierarchy: Note Brief needs to feel like a concise document overview, cue cards need to be clearly attached to headings without stealing attention, and category or keyword metadata must avoid becoming decorative noise.

Impact Map

Proposed changes 1-7

C1. Note Brief C2. Cue Width C3. Heading Chip C4. Rail Gutter C5. Typography C6. Divider C7. Shared Surface
C1.

Make Note Brief more editorial.

Impact: The brief becomes the calm overview at the top of the note instead of another dense generated panel.

User-visible change: The summary gets more breathing room, a full-width divider separates summary from insights, and the three insight columns use stable labels such as CORE IDEA, REVIEW FIRST, and SELF-TEST.

C2.

Constrain cue card width.

Impact: The cue rail stops feeling like a competing document column and returns focus to the markdown body.

User-visible change: Anchored rail cards should settle around the reference width rather than stretching wide enough to become mini articles.

C3.

Strengthen section heading and tag pairing.

Impact: A small heading-side chip can make the section's conceptual hook visible before the user reads the cue card.

Constraint: Do not use the current cue.category enum for this general purpose. It is coding-interview-specific and should not label unrelated notes.

C4.

Increase separation between cue rail and note content.

Impact: The cue card still feels anchored to the heading, but the note text has enough room to remain the primary reading surface.

User-visible change: The left rail gains a more intentional gutter, with cue cards top-aligned to the section they support.

C5.

Soften cue card typography.

Impact: The question remains the hero inside the cue card without becoming louder than the note heading.

User-visible change: Dense rail questions use slightly lighter weight and calmer sizing, especially when generated questions wrap across several lines.

C6.

Use one primary divider inside cue cards.

Impact: The card reads as question first, then quiet supporting terms, matching the reference's simple scan path.

Open product choice: Section Lens should either be hidden in anchored rail mode or demoted into quiet body text without its own label and divider.

C7.

Align Note Brief and cue cards visually.

Impact: The top brief and left rail feel like one design system rather than separate generated widgets.

User-visible change: Padding, border tone, radius, shadow, dividers, and muted chip treatment should match closely across surfaces.

Visual Shape

The intended hierarchy is note first, support second.

Product Requirements

Requirements

R1.

Note Brief must read as an editorial overview.

It uses a larger summary line, stable insight labels, and a divider before the three insight columns.

R2.

Anchored cue cards must stay compact.

The rail card width and typography should support fast scanning without overpowering the adjacent markdown section.

R3.

Heading-side chips must be domain-neutral.

If a heading chip is added, it must come from a general primaryTerm or equivalent field, not the current coding-specific cue.category enum.

R4.

The cue rail must preserve markdown primacy.

Spacing between the rail and section content should make cues feel attached to headings while keeping the note body easy to read.

R5.

Cue typography must remain quiet.

The question should be emphasized inside the card, but long generated questions must not look heavier than the note heading.

R6.

Anchored cue cards should have one primary internal divider.

The default scan path should be QUESTION, question text, divider, and TERMS chips.

R7.

All generated surfaces must share one card system.

Note Brief, cue cards, and tags should use the same background, border, radius, shadow, and muted metadata treatment.

Acceptance Examples

Acceptance Examples

AE1.

Note Brief hierarchy

Trigger: A generated Note Brief appears at the top of a note. Covers R1, R7. The summary reads as the dominant content, the insight grid starts after a full-width divider, and only dividers between insight columns are visible.

AE2.

Compact anchored cue

Trigger: A cue card is displayed in anchored rail mode. Covers R2, R4, R5, R6. The card is narrow, top-aligned with its heading, separated from the note body by a comfortable gutter, and structured as question followed by one divider and terms.

AE3.

Domain-neutral heading chip

Trigger: A section has a generated heading-side term. Covers R3. The term appears only if it is domain-neutral; coding-only values such as sequences, linkedlists, stacks, and intervals do not become general note labels.

Scope Boundaries

Scope Boundaries

In scope

Visual hierarchy, rail width, Note Brief editorial structure, quiet term chip styling, divider behavior, and the product decision around a domain-neutral heading chip.

Deferred for planning

The exact implementation path for deriving primaryTerm, if that field is chosen, belongs in the implementation plan.

Out of scope

Using the current coding-interview category enum as a general labeling system, adding decorative color fills, or turning the note into a dashboard layout.

Dependencies / Assumptions

Dependencies and Assumptions

Assumption: The current cue.category field remains useful only for coding-interview category accents unless the product model is generalized. A general heading chip requires either an optional domain-neutral term field or an explicit decision to omit the chip for now.

Appendix

Sources / Research

The visual reference and follow-up screenshots supplied in the working thread establish the intended hierarchy, term chip style, divider length, icon placement, and Note Brief column-divider behavior.

Resolved Product Note

cue.category is not a good source for a general section chip because its values are tied to coding interview patterns. The safer requirement is a domain-neutral primary term or no heading chip.

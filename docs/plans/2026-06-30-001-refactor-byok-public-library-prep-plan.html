Objective

Make the future BYOK package boundary explicit, portable, tested, and documented before copying it into a public repository.

Authority hierarchy

Follow docs/byok-extraction.md first, then the current BYOK public-contract tests, then current TypeScript/npm package guidance.

Stop conditions

Stop if the work requires changing BYOK's product identity into a generic chat SDK, adding new providers, or moving credential persistence into the package.

Execution profile

Standard-to-deep refactor. Land in small units inside CueCraft first, then extract only after CueCraft consumes the package-shaped public surface end to end.

Product Contract

Product Contract

Problem Frame

src/byok already has a strong extraction doc and import-boundary tests, but the package candidate is not yet a true standalone library. Its public barrel is wider than the documented API, provider code imports CueCraft-level schemas and generation guidance, some messages still name CueCraft or Obsidian, and Node CLI support is not isolated from browser-safe imports.

Success Criteria

A future public repository can copy the package candidate, publish typed entrypoints, run consumer smoke tests from packed output, and show consumers how to use providers without depending on CueCraft internals or storage policy.

A1. Library maintainer A2. CueCraft adapter A3. External JS/TS consumer A4. Release reviewer

Acceptance Examples

Acceptance Examples

AE1.

When a TypeScript app imports createByokProvider and public types from the main entrypoint, it can create an OpenAI or Ollama runtime without importing provider internals.

AE2.

When a browser-safe consumer imports the main entrypoint, the packed artifact does not require node:child_process, node:os, or node:stream.

AE3.

When the package is packed, the archive contains built JS, declarations, README, license, and package metadata, but not CueCraft plugin UI or Obsidian settings files.

AE4.

When a README example changes, CI catches drift by compiling or typechecking that example against the public package entrypoints.

Scope Boundaries

Scope Boundaries

In scope

Public API trimming, package-owned type/schema relocation, package topology, docs-as-tests, pack verification, and release governance.

Deferred to follow-up work

Creating the public GitHub repository, publishing to npm, and moving CueCraft to a remote package dependency after local package-shaped consumption is proven.

Outside product identity

Adding new providers, becoming a generic chat-completions SDK, or owning API-key encryption and persistence inside BYOK.

Planning Contract

Key Technical Decisions

KTD1. Public barrel is the API

Replace wildcard exports in src/byok/index.ts with explicit exports that match docs/byok-extraction.md. This prevents helpers from becoming semver commitments by accident.

KTD2. BYOK remains cue-domain runtime

Move or rename cue output schemas and generation option guidance into the package candidate rather than widening the package into a generic chat SDK.

KTD3. Split core and Node CLI entrypoints

Keep cloud and Ollama runtime APIs on the main entrypoint. Put Codex/Claude CLI providers and command-runner code behind a Node-only subpath.

KTD4. Apps own storage and branding

The library accepts resolved runtime secrets and neutral provider metadata. CueCraft-specific secure storage and wording stay in src/byok-cuecraft-adapter.ts or UI code.

KTD5. Publish readiness is proven by pack consumers

Unit tests remain necessary, but release readiness requires installing or importing packed output in consumer fixtures so manifest, exports, declarations, and dependency topology are exercised together.

High-Level Technical Design

High-Level Technical Design

The preparation path has two layers: harden the package-shaped boundary inside CueCraft, then extract to a public repository only after consumer-style validation passes.

Approach, tests, and verification

U3.

U3. Split core and Node-only entrypoints

Goal
Prevent browser-safe imports from loading local CLI code.
Requirements
R3, AE2
Dependencies
U1, U2
Files
src/byok/index.ts, src/byok/node.ts, src/byok/providers/local-command-runner.ts, CLI provider tests
Approach, tests, and verification

Approach: Keep cloud providers, Ollama, metadata, model helpers, and setup status on the main entrypoint. Move Codex/Claude CLI constructors and command-runner exports to a Node-only subpath so package exports can express runtime separation.

Technical design: The main entrypoint is suitable for Electron/browser-like environments. The Node subpath is opt-in and owns node:child_process, node:os, and node:stream dependencies.

Test scenarios: Verify main-entry imports do not reference Node built-ins. Verify Node subpath exports CLI providers. Verify CueCraft can still create CLI providers through the app adapter.

Verification: Import-boundary and consumer fixture tests prove the split from built output, not only source text.

Verification Contract

Verification Contract

Existing project gates

Run the repo's typecheck, test, and production build scripts after package-boundary changes. These cover current CueCraft behavior while the package is still internal.

Boundary gates

Keep and expand BYOK import-boundary and public-contract tests so forbidden Obsidian/UI/storage imports and undocumented public exports fail fast.

Package gates

Generate declaration output, inspect packed files, and compile external consumer fixtures against packed entrypoints.

Docs gates

Compile or typecheck public README examples, especially quickstart, custom transport, credential policy, model listing, and Node CLI import examples.

Risks & Dependencies

Risks & Dependencies

Risk

Accidental public API expansion through wildcard exports creates semver commitments before the package has external users.

Risk

Node CLI code can make the main package unusable in browser-like environments if entrypoints are not split and tested from packed output.

Dependency

Package publishing depends on a package manifest, declaration build, CI gates, and future npm/GitHub trusted publishing setup.

Assumption

The package name remains undecided. The plan works for a scoped name such as @cuecraft/byok or a later neutral name.

System-Wide Impact

System-Wide Impact

CueCraft app

CueCraft keeps storage, settings UI, Obsidian transport adaptation, and note/cache orchestration. Its adapter becomes the proof that the package API is usable from a real app.

Future consumers

Consumers get provider creation, model listing, cue/summary generation, capability metadata, typed configs, and clear runtime dependencies without app-specific settings assumptions.

Contributor workflow

Provider additions and API changes require public-contract updates, docs examples, declaration output, and pack-consumer validation.

Release posture

Public release becomes an API governance event, not a copy-paste of current source into a new repository.

Definition of Done

Definition of Done

API

The public barrel and optional Node-only subpath are explicit, documented, and covered by contract tests.

Boundary

Package-owned source no longer depends on CueCraft-only schema or generation modules, Obsidian settings, storage adapters, DOM UI, or plugin runtime files.

Docs

Public README-shaped docs explain quickstart usage, transports, credential policy, model discovery, local CLI support, and troubleshooting.

Verification

Unit, type, build, boundary, docs, declaration, and pack-consumer checks all pass from current source and packed output.

Extraction readiness

CueCraft consumes the package-shaped API internally, and the release checklist is complete enough to create the public repo without re-deciding scope.

Cleanup

Dead compatibility shims, abandoned package experiments, and stale internal imports introduced during the work are removed before completion.
